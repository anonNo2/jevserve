# Releases and evidence

JevServe currently ships **development previews**, not certified releases. The
new manual workflow has CPU tests but has not been dispatched against GitHub or
Docker Hub. No release manifest is currently eligible. Historical dev0/dev1
reports remain useful observations; they do not establish all the source-commit
bindings required by this workflow. Do not add guessed commits to old reports.

The release tool uses only Python 3.12 standard-library code. Local review is
offline and does not require Docker, GPU libraries, weights or credentials:

```bash
.venv/bin/python -m validation.release releases/0.1.0-dev2.json \
  --expected-commit FULL_40_CHARACTER_TESTED_SOURCE_COMMIT
.venv/bin/pytest tests/contract/test_release_evidence.py -q
```

The manifest above is a future example path, not a file that currently exists.
Use a clean committed candidate, run the public validation runner on that exact
source and immutable registry digest, then commit its sanitized evidence and
release manifest in a later review commit. The tested source must be an ancestor
of the review checkout. Evidence commits need not rebuild the image. A changed
runtime, dependency or model requires a new candidate and new execution evidence.

## Eligibility and trust

| Channel | Policy |
| --- | --- |
| Development preview | Every shipped model revision must execute on a real GPU in the exact image. CPU, Docker, Compose and offline gates must have hash-bound reports. Measured failed probability parity must be explicitly listed. |
| Alpha | Disabled. Requires a separately implemented certification policy with real reference/parity evidence at frozen tolerances and both container paths. |
| RC | Disabled; additionally requires an actual 24-hour soak. |
| Stable | Disabled; additionally requires an actual 72-hour soak and clean-host installation. |

`--allow-uncertified`, a short synthetic test, matching labels, an image build,
and a green CPU job do not certify probabilities or stability. Preview metadata
must retain scope and license limitations, including separate text/vision claims.

The validator checks consistency and integrity of reviewed evidence; it cannot
prove that a person actually ran a command. Reviewers must inspect raw reports,
runner output and execution provenance. Gate attestations are explicitly human
reviewed records, not cryptographic hardware attestations. Do not copy a status
from an old image or synthesize an unperformed test to satisfy the schema.

## Manifest format (schema version 1)

The top-level JSON object has these required fields:

- `schema_version`: `1`; `channel`: `development-preview`.
- `version`: Docker tag in the form `0.1.0-dev2` (no `latest` alias).
- `source_commit`: full lowercase 40-character Git commit.
- `image_repository`: `anonwx/jevserve`; `image_digest`: registry manifest/index
  `sha256:` digest. A Docker configuration/image ID is insufficient.
- `source_files`: `{ "path": "...", "sha256": "..." }` entries for
  `compat/engine-lock.json`, `compat/runtime-requirements.txt`,
  `compat/reference-requirements.txt`, `uv.lock`, `pyproject.toml`, and **every**
  `src/jevserve/data/*.json` shipped at the source commit. Hashes are checked
  against Git objects at that commit, binding dependencies, model weights,
  tokenizer/base revisions and source manifests without copying weights.
- `limitations`: nonempty array of human-readable limitations.
- `failed_parity_models`: exact model IDs whose measured parity failed.
- `evidence`: one `{ "path": "...", "sha256": "..." }` aggregate report entry.

All report paths are repository relative, without symlinks or traversal. SHA-256
values are 64 lowercase hex characters. Duplicate JSON keys are rejected.

The aggregate report contains `schema_version`, `source_commit`, `image_digest`,
`real_gpu: true`, and `gates` with exactly `cpu`, `docker_run`, `compose`, `offline`
set to `passed`. Its `gate_reports` maps those same names to hashed report entries.
Each gate report contains:

```json
{
  "report_type": "jevserve-release-gate",
  "schema_version": 1,
  "source_commit": "FULL_TESTED_COMMIT",
  "image_digest": "sha256:TESTED_REGISTRY_DIGEST",
  "gate": "compose",
  "status": "passed",
  "commands": ["actual command that was executed"],
  "reports": [{"path": "validation/reports/actual-output.json", "sha256": "ACTUAL_HASH"}]
}
```

This is a format illustration, deliberately invalid as release evidence.
Record actual command output in the referenced reports. These gate wrappers are
reviewed attestations and are not currently generated by the model runner.

The aggregate `models` array must cover exactly all shipped model IDs/revisions.
Each entry includes `model_id`, `revision`, `execution: "passed"`, measured
`parity` (`passed` or `failed`), integer `parity_failed_cases`, and a nonempty
`reports` array of hashed files.
Exactly one of those files must be a public validation runner summary with
`report_type: "jevserve-validation"`. The validator checks its exact source/image/
model binding, `source_dirty: false`, real GPU flag, successful execution and
cleanup, and agreement on parity. It also checks hashes of the summary's
`reference.json` and `http.json` (and any additional referenced reports), resolved
relative to the summary's directory. Both known raw report formats are parsed:
model revisions, nonempty case coverage, successful HTTP responses, SDK execution,
and measured per-case parity must agree with raw, summary and aggregate failure
counts. The Open-Jev format additionally binds its HTTP report to the reference
hash and checks CUDA reference success; matrix reports do not invent those fields.
Legacy reports cannot substitute for the source-bound runner summary.

## Protected manual promotion

Before enabling `.github/workflows/release.yml`, maintainers must configure:

1. Protect `main` and require review of workflow, validator, manifests and evidence.
2. Create GitHub environment `release`, restrict deployment to `main`, require
   reviewer approval and prevent self-review where available. Restrict bypass.
3. Add environment secrets `DOCKERHUB_USERNAME` and `DOCKERHUB_TOKEN`, using a token
   with the minimum push access for `anonwx/jevserve`. Never store it in Git or
   command arguments. Keep other writers from racing the release tag.
4. Merge the reviewed manifest and evidence. Run **Reviewed development image
   promotion** manually on `main`, supplying the manifest path and exact tested
   source SHA. Inspect the validation job, then approve the environment deployment.

Only `workflow_dispatch` is enabled. The job rejects other repositories/branches,
uses GitHub-hosted CPU runners, and checks out the exact workflow commit with a
full-SHA-pinned checkout action and no persisted Git credentials. Pull requests,
forks and `pull_request_target` do not invoke this release workflow. Shared GPU
runners and credentials are not exposed to contributed code.

Promotion revalidates the reviewed files. It authenticates directly to Docker
Hub over HTTPS using environment secrets, refuses redirects, retrieves the
already-tested registry manifest and verifies its bytes against the declared
digest. It refuses an existing target tag and PUTs the **same bytes** under the
new version in the same repository, then verifies the destination bytes. There
is no rebuild, serialization, annotation change or platform filtering. Registry
errors abort; a post-write verification failure requires manual inspection before
retrying. Registry tag writes are not atomic compare-and-swap, so restrict other
writers and use unique version tags. This workflow serializes its own releases.

It creates no Git tag, GitHub Release, PyPI package or `latest` tag. Publish those
separately only with authorization and the same reviewed source/evidence. The
workflow summary, committed manifest and immutable digest form the promotion
record. Do not claim remote publication succeeded from local policy tests.

Protocol references: [Docker Registry HTTP API V2](https://distribution.github.io/distribution/spec/api/)
and [GitHub workflow dispatch](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#workflow_dispatch).
